A **profile** is a named thing you can put in a pane. Shells and applications are the same idea —
to the layout they are both a program, some arguments and a working directory — so they are the same
list.

The shipped terminals are seeded on first run and are editable and deletable like anything else.

## Adding one

**Settings → Profiles**, or `Add or edit profiles…` in the New menu:

- **Add application…** browses the installed-application catalogue, read from the Start Menu and
  resolved through the shortcuts. You should not have to know where an executable lives.
- **Add manually…** takes a path you type or browse to.

Whatever you add appears everywhere at once: the New menu, an empty pane's launcher, the command
palette and the CLI, because all of them read the same list.

## Remote connections

An **SSH** or **Remote Desktop** connection is a profile too, which is the point: saving one adds it
to the New menu, an empty pane's launcher, the command palette and the CLI at once, exactly like a
local program.

Choose `SSH connection` or `Remote Desktop connection` in the profile editor and fill in the host —
plus, optionally, a port, a user and an SSH identity file. WinMux builds the command:

| Kind | Runs | Opens |
|---|---|---|
| SSH | `ssh.exe [-p port] [-i identity] [user@]host` | a terminal pane |
| Remote Desktop | `mstsc.exe /v:host[:port]` | a hosted application pane |
| SFTP | nothing — WinMux speaks it | a file-browser pane on the remote |
| FTP | nothing — WinMux speaks it | a file-browser pane on the remote |

Both clients ship with Windows, so there is nothing to install. The default port is left off the
command line rather than passed explicitly, so an SSH connection still honours whatever your
`ssh_config` says about that host. Anything in the profile's **Arguments** is appended last, so it
can override what WinMux built.

<Aside type="caution" title="No passwords, deliberately">
WinMux stores no password, for any connection, anywhere. The profiles file is plain text and always
will be.

SSH uses your agent and your keys. Remote Desktop prompts and — if you tick the box — remembers the
credential in **Windows Credential Manager**, which is the system's own encrypted store and the
right place for it. That is also why the Remote Desktop connection has no user field on the command
line: `mstsc` has no switch for one, and adding a half-built credential store to work around that
would be worse than using the one Windows provides.
</Aside>

Network shares are the other half of working remotely, and they work differently: Windows mounts
them and WinMux just uses the path. See [Network shares](/network-shares/).

### Browsing a server

**SFTP** and **FTP** are different from the other two: there is no Windows client to hand them to,
so WinMux implements them, and the pane you get is the ordinary file browser pointed somewhere else.
Everything in [Keyboard](/keyboard/#in-a-file-browser-pane) works the same — new folder, rename,
copy, paste, delete — because it is the same browser.

Two differences you will notice, both of them the protocol's doing rather than a gap:

- **There is no Recycle Bin on a server.** `Delete` says so and refuses; `Shift+Delete` deletes, and
  asks first. WinMux does not invent a hidden trash folder, because that is a promise it could not
  keep the moment anyone touched the server by other means.
- **Copying is a download and an upload.** Neither protocol has a server-side copy, so duplicating a
  large file on the server costs its size twice over the wire. There is no way around that from a
  client.

**SFTP can use a key.** Put the private key file in the profile's identity field and there is no
password to type or store. Otherwise WinMux asks once and offers to keep it in Windows Credential
Manager.

**SCP has no entry of its own**, deliberately. It is a copy command with no directory listing — there
is nothing for a browser to show — and every server that speaks SCP speaks SFTP.

<Aside type="caution" title="Plain FTP is clear text">
FTP sends your password and your files unencrypted. WinMux asks for FTPS and uses it whenever the
server offers it, and the sign-in dialog says so plainly when it cannot. A server with no encryption
still connects, because those are exactly the old devices that have nothing else — but know what you
are sending. SFTP has no such problem.
</Aside>

## Hosting an application

Ordinary applications are **embedded**: the window becomes a child of a host process that WinMux
positions over the pane. The host is a separate process on purpose — a frozen application freezes
its own host, and WinMux stays alive and can detach or close the pane.

Some applications refuse. WinMux detects the refusal and switches to **attach**, leaving the window
top-level and driving its position to follow the pane, like a tiling window manager. Less seamless,
far more compatible. `Ctrl+B` `a` switches a pane between the two at any time, and the choice is
remembered per application.

<Aside title="Detaching is always safe">
Every embed is undoable. Closing a pane restores the window's parent, styles and rectangle exactly
as they were, and the application keeps running. An orphaned invisible window would be a lost
application, so the restore happens before anything else.
</Aside>

## Adopting a window that is already open

`Ctrl+B` `o` opens a tray of the windows currently open. **Drag one onto a pane** and it is adopted
there.

Dragging the application's *own* window from the desktop onto WinMux is not possible — Windows
delivers a window-move to the window being moved, not to whatever it passes over, so there is no
drop for WinMux to receive. Dragging its entry out of the tray is the same gesture over something
WinMux owns.

An adopted pane records the program's path, so the next session starts the same program rather than
chasing a window handle that will not exist.

## The quirks database

`foreign-app-quirks.json` beside the executable maps applications to a hosting strategy, a
window-selection rule, a launch delay and any known limitations. It is deliberately user-editable —
if an application needs different treatment, that is where to say so.

Matching is on executable image, window class and an optional title substring. Never on the launched
process id: on Windows 11 `notepad.exe` is a shim that runs a *different* process.
